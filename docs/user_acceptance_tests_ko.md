# NyaNya Agent 사용자 수용 테스트

이 문서는 소스 전체를 읽지 않고도 핵심 기능이 실제로 동작하는지 확인하기 위한 체크리스트다. 테스트 메시지에는 비밀번호, 토큰, 개인 경로 또는 계정 식별자를 넣지 않는다.

2026-09-21 갱신: 기존 다섯 시나리오에 P0 파일 승인·복구·병렬성 세 가지를 추가했다.
아래는 실행 계획이며 통과 기록이 아니다. [개발 현황](development_status.md)의
수정 대기 항목을 먼저 검토하고, 실제 계정에 등록한 격리 테스트 workspace를 사용한다.
서비스 중단·재시작과 테스트 파일 수정은 해당 운영 테스트 범위가 승인된 때에만 수행한다.
실제 계정/작업 ID/경로/메시지와 증거는 공개 체크리스트 대신 로컬 비공개 기록에 남긴다.

## 공통 판정

- `통과`: 기대 결과가 모두 보이고 오류 메시지가 없다.
- `부분 통과`: 핵심 결과는 보이지만 진행 상태 또는 대시보드 기록이 빠진다.
- `실패`: 응답이 없거나 권한·인증·파일 전송 오류가 발생한다.

## TC-01 로컬 서비스와 대시보드

터미널에서 다음을 실행한다.

```bash
./scripts/nyanya_ctl.sh status-all
./scripts/nyanya_ctl.sh dashboard-health
```

브라우저에서 `http://127.0.0.1:8765/#office`를 연다.

기대 결과:

- Discord bridge, dashboard, memory worker가 `running` 또는 `active`다.
- dashboard health가 `status=ok`다.
- Agent Office 화면과 접근 가능한 상태 목록이 표시된다.

## TC-02 Discord 제어 명령

허용된 Discord 채널에서 차례로 보낸다.

```text
!nyanya status
!nyanya tasks
```

기대 결과:

- `status`가 bridge와 backend 구성을 요약한다.
- `tasks`가 현재 사용자의 활성·대기 작업을 보여준다. 완료 결과는
  `result 작업ID` 또는 dashboard Tasks/Executions에서 별도로 확인한다.
- 다른 사용자의 작업이나 비밀 설정값은 노출되지 않는다.

## TC-03 LLM 기본 응답

허용된 Discord 채널에서 다음과 같이 보낸다.

```text
!nyanya 현재 NyaNya Agent가 제공하는 기능을 다섯 줄로 요약해줘.
```

기대 결과:

- 접수 메시지가 먼저 표시된다.
- 오래 걸리면 계획 또는 진행 상태가 중간에 표시된다.
- 마지막에 한국어 결과가 한 번만 표시된다.
- 대시보드의 Tasks 또는 Executions에서 같은 요청을 찾을 수 있다.

현재 구현은 접수 안내/최종 결과 watcher를 갖지만 전송 순서와 중간 진행 heartbeat는
보장하지 않는다. 위 순서·진행 항목이 빠지면 부분 통과로 기록한다. 정상 연결에서
한 번 수신했다는 결과로 재접속·프로세스 장애에서도 정확히 한 번 전달된다고 판정하지 않는다.

## TC-04 Codex 읽기 전용 작업과 진행 조회

허용된 Discord 채널에서 다음과 같이 보낸다.

```text
!nyanya codex README.md와 README.KO.md만 읽고 문서 구조의 차이를 다섯 가지로 정리해줘.
```

작업 중에 다음을 보낸다.

```text
!nyanya tasks
```

기대 결과:

- Codex 작업이 읽기 전용 profile로 시작된다.
- `tasks`에서 대기 또는 진행 상태를 확인할 수 있다.
- 작업 완료 후 요약이 표시되고 저장소 파일은 변경되지 않는다.

`codex`는 Flash 판단 후 Luna/Codex 실행을 선택한다. 요청한 파일이 제한된 snapshot에
들어갈 수 있도록 작은 테스트 workspace를 준비한다. 일부만 읽은 결과를 전체 검토로
판정하지 않는다. 별도 외부 Codex 대화 세션 재개를 확인하는 테스트는 아니다.

## TC-05 일반 채널 요청 파일을 자료공유로 전송

관리자가 준비한 테스트 파일을 일반 채널에서 업로드 요청한다.

```text
!nyanya upload docs/private/nyanya_uat_sample.txt
```

기대 결과:

- 일반 채널에는 업로드 결과만 간단히 표시된다.
- 설정된 `자료공유` 채널에 테스트 파일이 정확히 한 번 첨부된다.
- 토큰, 절대 홈 경로 또는 내부 채널 식별자가 메시지에 나타나지 않는다.

정상 연결의 업로드 확인이다. 업로드 callback에는 durable outbox가 없으므로
장애 후 중복 없는 재전달까지 통과로 간주하지 않는다.

## TC-06 파일 생성과 기존 파일 승인

격리 workspace에 민감하지 않은 UTF-8 일반 테스트 파일을 준비한다.
신규 문서 생성을 요청하여 날짜/작업 폴더 아래에 생성되는지 확인한다.
기존 테스트 파일 수정 요청을 보내고 `plan 변경안ID`, 필요하면
`plan-file 변경안ID 상대경로`로 변경 내용과 hash를 확인한다.

기대 결과:

- 신규 생성이 기존 경로를 덮어쓰지 않는다.
- 기존 파일은 승인 전 동일하며, 변경 경로·이유·전후 내용이 보인다.
- 올바른 `approve 변경안ID plan_hash` 후에만 검토한 변경이 적용된다.
- 잘못된 hash나 `revoke 변경안ID`로 철회한 변경안은 적용되지 않는다.
- 변경안 검토 뒤 원본이 바뀌면 기존 승인을 이용해 덮어쓰지 않는다.

성공 경로와 거절 경로는 서로 다른 테스트 요청으로 기록한다.

## TC-07 중단 보류·진단·상기·재개

파일 효과가 없는 테스트 요청을 접수한 뒤, 별도로 승인된 운영 드릴에서만 worker나
controller 중단/복구를 수행한다. `recovery`, `why 작업ID`로 확인한 후 독립된
새 요청을 완료한다. 이전 요청을 재개하려면 명시적으로 `resume 작업ID`를 보낸다.

기대 결과:

- 중단된 요청이 자동 재실행되지 않고 보류 이유와 원래 요청을 조회할 수 있다.
- 새 요청 완료 시 이전 미완료 작업이 상기된다.
- 명시적 재개는 새 시도로 기록되고 이전 결과가 새 결과로 재전달되지 않는다.
- 파일 적용 중단은 위 재개와 분리하여 `reconcile 변경안ID`로 관측하고,
  검토한 관측 hash로 `resolve 변경안ID 관측hash`를 수행한다.
- resolve가 파일을 재실행하거나 rollback하지 않는다. 일부 적용이면 새 변경안을 만든다.

파일 적용 중단 드릴은 추가 승인과 테스트 파일 백업이 필요하다. 현재 REV-01
재시도 대기 결함의 수정 여부도 기록한다. 운영 요청을 임의로 재시도하지 않는다.

## TC-08 독립 요청 병렬성과 모델 선택

동시 실행 한도가 2 이상인 격리 환경에서 서로 독립된 읽기/분석 요청 두 개를 접수한다.
Tasks/Executions와 이벤트에서 실행 시간의 중첩, 평가 점수와 선택 profile을 확인한다.

기대 결과:

- 충분히 긴 두 요청이 설정된 한도 내에서 동시에 실행된다.
- 각각 Flash 판단과 선택 모델 기록이 있고 결과가 서로 섞이지 않는다.

이것은 여러 요청의 병렬 처리다. 한 요청을 여러 에이전트로 나누는 DAG 기능은
미구현이므로 이 테스트 결과로 해당 기능을 통과 처리하지 않는다.
동일 workspace의 동시 파일 적용도 이 읽기 테스트의 검증 범위가 아니다.
