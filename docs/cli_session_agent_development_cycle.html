NyaNya Agent architecture note

CLI 세션형 에이전트를 만들려면 무엇이 달라져야 하는가

Claude Code, Codex, Antigravity CLI 같은 도구는 단순히 프롬프트 한 번을 외부 모델에 넘기는 프로그램이 아니다. 세션, 컨텍스트 예산, 압축, 도구 권한, 파일 작업, 재개 가능한 실행 상태를 가진 런타임이다.

1. 현재 냐냐에이전트의 성격

현재 냐냐에이전트는 로컬-first messenger bridge와 lightweight CLI wrapper에 가깝다. Discord/Telegram에서 요청을 받고, 허용 workspace와 보호 경로를 검사한 뒤, Gemini/Antigravity CLI 또는 Codex CLI 같은 외부 실행기를 호출한다.

강점

구조가 작고, 설치와 이해가 쉽고, Discord/Telegram 자동화에 바로 쓸 수 있다.

역할

직접 모델 런타임이라기보다 메시지 수신, 정책 검사, 외부 CLI 위임을 담당하는 router다.

한계

긴 세션을 자체 관리하거나, 컨텍스트 압축을 자체 수행하거나, 도구 실행 그래프를 자체적으로 유지하지 않는다.

2. CLI 세션형 에이전트와의 차이

항목 현재 냐냐에이전트 CLI 세션형 에이전트
세션 메신저 대화별 in-memory 메시지 일부를 보관한다. 세션 ID, 작업 디렉토리, 파일 diff, tool 결과, plan 상태, 압축 요약을 지속 저장한다.
컨텍스트 관리 최근 메시지를 제한적으로 유지하고 외부 CLI에 전달한다. 토큰 예산을 계산하고, 오래된 대화와 tool 결과를 요약/압축하며, 필요한 파일만 다시 주입한다.
도구 실행 Codex CLI, Gemini/Antigravity CLI 같은 외부 프로세스에 위임한다. 자체 tool registry, MCP client, plugin/skill loader, 권한 승인, sandbox 실행기를 갖는다.
작업 상태 작업 큐와 취소 이벤트 중심이다. 단계별 plan, 중간 산출물, tool call history, 실패 복구 지점, resume state를 가진다.
파일 변경 직접 수정은 제한적이고, 복잡한 작업은 Codex에 맡긴다. 파일 읽기/쓰기/패치/검증/rollback 전략을 자체적으로 설계한다.
사용자 인터페이스 Discord/Telegram/간단 CLI 중심이다. TTY streaming, 승인 prompt, diff view, plan update, 세션 resume, 로그 조회를 제공한다.

3. 필요한 내부 구성요소

Session Kernel

세션 생성, 재개, 종료, 현재 작업 디렉토리, 모델 설정, 사용자 권한을 하나의 상태 객체로 관리한다.

Context Manager

대화, 파일 스냅샷, tool 결과, 요약문을 토큰 예산 안에 넣도록 선택하고 압축한다.

Tool Runtime

shell, file, browser, MCP, app connector, plugin tool을 공통 schema와 permission model로 실행한다.

Skill Loader

작업 유형별 지침, 예제, 스크립트, 템플릿을 로딩하고 해당 세션의 system context에 반영한다.

Safety Layer

allowed roots, secret redaction, destructive action approval, network/file 권한, audit log를 강제한다.

Renderer and Reporter

CLI 출력, Discord 답변, HTML 보고서, diff 요약, 실패 원인 보고를 같은 작업 상태에서 생성한다.

4. 개발 사이클

1

요구사항 정의

지원할 채널, tool 종류, 파일 권한, 세션 지속 범위, 모델 provider를 정한다.

2

세션 모델 설계

session id, messages, summaries, tool calls, workspace, approvals, artifacts schema를 만든다.

3

도구 계층 구현

file, shell, MCP, plugin, app connector를 같은 호출 규약으로 묶는다.

4

컨텍스트 압축

토큰 한계 도달 전 요약하고, 원문이 필요한 evidence는 파일/로그 참조로 유지한다.

5

검증 루프

작업 결과를 테스트, lint, render, diff, 사용자 승인으로 확인한 뒤 세션에 기록한다.

5. 냐냐에이전트에서 진화시키는 순서

단계 추가할 것 판단 기준
1단계 세션 저장소를 JSON/SQLite로 영속화 브리지 재시작 후에도 대화, 대기 작업, 요약 상태를 이어갈 수 있어야 한다.
2단계 tool call record와 artifact registry 어떤 명령을 왜 실행했고 어떤 파일을 만들었는지 추적할 수 있어야 한다.
3단계 MCP/plugin/skill loader 로컬 파일로 등록된 tool과 skill을 세션 시작 시 안전하게 불러와야 한다.
4단계 context compaction engine 긴 작업 중에도 중요한 결정, 파일 경로, 테스트 결과, 남은 TODO가 보존되어야 한다.
5단계 interactive CLI UI 사용자가 터미널에서 plan, 승인 요청, diff, tool log, resume을 볼 수 있어야 한다.
6단계 sandbox and approval policy 읽기, 쓰기, 네트워크, 외부 앱 제어가 정책과 사용자 승인에 의해 제한되어야 한다.

6. 구현 우선순위

먼저 할 것

현재 구조를 유지하면서 세션 저장소, tool call log, context summary 파일을 추가한다. 이 단계는 Discord/Telegram bridge를 깨지 않고도 진행할 수 있다.

나중에 할 것

자체 모델 runtime, 완전한 TUI, MCP host, plugin marketplace, 브라우저 제어는 구조가 안정된 뒤 추가한다. 처음부터 모두 만들면 디버깅 범위가 지나치게 커진다.

결론: 냐냐에이전트를 CLI 세션형 에이전트로 발전시키려면 "외부 CLI 호출 wrapper"에서 "세션 상태와 도구 실행을 직접 소유하는 runtime"으로 중심을 옮겨야 한다.
